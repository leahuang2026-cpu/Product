## 1. 当前结论

产品定位已明确：Personal OS 以个人知识与人生档案为核心，AI 辅助整理、讨论和复盘，帮助用户连接过去的沉淀、现在的关注与未来的方向。核心用户是本人，真实使用价值优先于商业化。

尚未明确的是首版范围和行为规则。历史对话中的 P0/P1、勾选清单、页面导航、对象模型、默认提醒频率和技术栈，主要由 AI 提出。用户后续继续讨论、询问是否转向 Codex、表示已发送第一条任务，都不足以证明已经逐项批准这些方案。

最小产品价值可概括为：值得保存的内容不丢失；需要时能重新找到；能看见本阶段为何关注这些事情；需要思考时有基于记录的讨论与复盘。这是本次分析归纳，不是新增用户需求。

### 2.1 如何认定需求

- **明确需求**：用户原话直接提出，或本轮重新明确。表示产品需要，不等于承诺首版全部实现。
- **建议待确认**：历史 AI 提案或本次分析建议，未找到用户逐项确认。
- **发生变化**：有前后证据说明重心、边界或内容变化；不能把 AI 自行调整的优先级写成用户决策。
- **歧义／冲突**：多个合理解释会改变范围、交互或数据处理，需要 Owner 判断。
- **待验证假设**：关于使用频率、维护成本、效果的推测；不能写成已观察事实。

| 项目文档   | 用户希望文档记录开发全过程（H-U6）        | 本轮要求九类交付、保留演进（N2、N3）                  | 文档目标明确；数量、目录和更新粒度应控制成本                      |

## 6. 产品分析

### 6.1 目标与成功信号

| 用户问题                         | 对应需求      | 候选成功信号（待验证，不是既定 KPI）                         |
| -------------------------------- | ------------- | ------------------------------------------------------------ |
| 想法、经历和内容容易散落或被忘记 | R06、R07      | 真实记录可以迅速存下，之后找得到；不要求当场完整分类         |
| 历史积累难以支持当前思考         | R11、R14      | 用户能在实际讨论中找回一条有用旧记录，并识别其来源和当时语境 |
| 长期方向与当期忙碌脱节           | R12–R14       | 打开当前关注时，能理解“正在关注什么、为什么”                 |
| 不希望每个念头变成任务或压力     | R08、R09、R25 | 灵感可停留、生活记录可独立存在，不因未转项目而反复催促       |
| 希望借 AI 反思，但保留自己的判断 | R10、R15、R23 | AI 观点与用户判断可区分；调整目标由用户决定                  |
| 系统本身可能成为维护负担         | R25           | 一段时间未使用后能直接继续；无需先清空积压记录或补打卡       |

### 6.2 核心场景草稿

以下是由已明确需求重建的场景，不代表已经观察到的使用行为。

| 场景                     | 用户目的                 | 关键流程候选                                    | 尚待确认                                     |
| ------------------------ | ------------------------ | ----------------------------------------------- | -------------------------------------------- |
| 随手记下一句心情         | 保留当时感受             | 输入→保存→明确反馈成功                          | 是否有任何后台 AI 处理；是否默认分类         |
| 上传一段语音、截图或链接 | 避免遗失信息             | 提交→保存原始材料→按允许范围转写或提取          | 哪些输入首版必须；解析时机；链接失效如何处理 |
| 留下一个副业或产品灵感   | 为未来保留可能性         | 保存为灵感→可继续讨论→也可长期不行动            | 灵感是否独立页面；最少需要哪些状态           |
| 打开系统查看当前重点     | 重新建立行动上下文       | 查看当前关注→看相关方向／项目→看下一步          | 是否必须桌面常驻；是否需要独立任务系统       |
| 再次思考曾经讨论过的问题 | 找回旧观点并发展判断     | 检索旧记录→查看原文／时间→选择加入讨论          | AI 可自动检索哪些范围；是否自动写回新结论    |
| 阶段回顾                 | 了解变化，决定继续或调整 | 选时间和材料→阅读回顾→确认个人判断→选择调整关注 | 手动或定时；周期；哪些数据可供 AI 使用       |
| 将部分沉淀公开           | 展示作品或表达观点       | 选择内容→检查范围→预览→发布                     | 首版是否需要；单条发布还是独立副本           |

### 6.3 五个领域与三种时间视角

五领域回答“内容与人生的哪些方面有关”；Memory／Focus／Direction 回答“这些内容如何连接过去、现在、未来”。两者可以交叉，但不应要求用户为每条记录填写所有维度。

**本次建议**：五领域作为可选的组织线索；Memory／Focus／Direction 作为查看和思考方式。不要先建立十五个空栏目，再要求用户不断填满。此处为信息组织建议，尚未确定导航。

### 6.4 灵感、记录、项目、目标、任务的关系

| 概念           | 建议的业务含义                               | 必须避免的混淆                                       |
| -------------- | -------------------------------------------- | ---------------------------------------------------- |
| 记录 Record    | 保存一次输入、经历或思考的内容               | 记录不等于行动承诺                                   |
| 灵感 Idea      | 值得保留或探索的可能性；可以是记录的一种类型 | 不因保存就生成截止日期、任务或项目                   |
| 项目 Project   | 用户已决定推进、有预期结果的一段工作         | 灵感与项目可以关联，原始灵感不应因“转化”而丢失       |
| 方向 Direction | 长期希望靠近的状态或价值取向                 | 不必都有到期日、数值指标或完成率                     |
| 目标 Goal      | 在某个阶段希望实现的结果                     | 与长期方向是否共用一种对象，仍可简化设计             |
| 当前关注 Focus | 用户此阶段主动选出的重点及其意义             | 可以是视图或引用集合，不一定要成为另一套重复数据     |
| 任务／下一步   | 推进项目或关注点的具体行动                   | 可先用简短下一步，不必直接引入完整任务管理           |
| 复盘 Review    | 基于既有材料形成的回顾和判断                 | AI 草稿与用户认可的判断应区分                        |
| 决策／作品     | 值得保留的选择依据或成果                     | 可以先作为记录内容／关联成果，不必一开始各建一套系统 |

**建议关系**：记录可关联灵感、项目或目标，也可不关联；项目和当前关注可关联一个或多个长期方向；灵感只有经用户选择才进入执行；讨论和复盘可以提出调整建议，不能自动改变当前关注。

关系本身服务于理解，不应变成必填路径。一次旅行、一条心情或一个尚未理解的想法，不需要为了入库而证明它服务于某个目标。

### 6.5 安静保存、深入讨论、定期复盘应分开定义

| 交互     | 用户已明确的期待             | 待定规则                                        | 本次建议                                                   |
| -------- | ---------------------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| 安静保存 | 先留下内容，不被评价或追问   | 转写／OCR／分类是否算默认处理；是否调用外部模型 | “保存成功”与“AI 处理完成”分开；允许保留原始材料后结束      |
| 深入讨论 | 对问题展开分析，能联系旧观点 | 谁发起、检索范围、结果保存方式                  | 由用户明确发起，可查看使用了哪些旧记录；观点先作为讨论结果 |
| 定期复盘 | 回看变化并帮助重新判断       | 提醒时间、材料范围、自动生成或手动开始          | 首次先用手动回顾验证价值，再决定是否固定提醒；尚待用户选择 |

“主动输入”规定信息从哪里来；“后台 AI 处理”规定输入后做什么；“发起通知”规定何时打扰用户。这是三个不同权限，不能用一个“智能开启”开关替代。

### 6.6 隐私、公开和数据归属

已明确：用户主动控制信息进入系统，个人网页可以只开放部分内容，AI 不代替人生决定。

以下为本次建议，需在正式 PRD 中确认后再落实：

- **三类边界分别控制**：是否保存在云端、是否交给模型处理、是否允许外部访问；同意其中一项不表示同意另外两项。
- **原始内容与派生内容分开**：保留原输入；转写、摘要、AI 观点可修正，不反向覆盖原始记录。
- **公开采用明确选择和预览**：标题、标签、附件、关联记录、摘要及搜索结果同样属于权限检查范围。
- **数据可带走**：导出应考虑文本、原始附件、时间、关联、个人判断和 AI 结果；只有纯文字导出不一定能还原档案。
- **删除有清楚后果**：需说明原始文件、摘要、搜索索引、AI 派生内容和备份的处理范围；不作尚未验证的即时彻底删除承诺。
- **开发记录与个人档案分开**：项目案例使用脱敏或示例内容；记录产品决策不要求复制私人日记和工作内部材料。
- **AI 可用范围可解释**：讨论可先从用户选定材料开始；全库自动关联、长期记忆范围和外部模型的数据处理政策应单独评审。

此处是产品边界分析，不是已完成的安全方案或法律结论。

### 6.7 维护负担及潜在风险

| 风险               | 具体触发方式                                 | 建议措施／待验证点                                       |
| ------------------ | -------------------------------------------- | -------------------------------------------------------- |
| 范围膨胀           | 五领域分别长成任务、财务、健康、内容运营工具 | 先验证共用的记录与复盘流程；领域专用功能按真实缺口增加   |
| 记录焦虑           | 每条内容要求标签、目标、阶段、下一步         | 大部分字段可选；不要求清空收件箱                         |
| 过度干预           | AI 看见情绪词就评价，发现灵感就催执行        | 保存、讨论、提醒分别授权；灵感默认无执行义务             |
| 错误归因           | AI 总结被长期记成用户真实观点                | 保留来源、作者属性和待确认状态；纠错不覆盖原始证据       |
| 旧目标绑架当前选择 | 已放弃目标继续进入提醒与建议                 | 建议保留历史并标明有效阶段，不再当作当前承诺             |
| 片面复盘           | 未记录的生活被推断为没有发生或没有投入       | 明确仅反映现有记录，允许用户补充、反驳或不接受结论       |
| 采集失败           | 音频未转写、图片未识别、链接不可访问         | 保存与解析分开反馈；解析失败不伪装成成功或虚构内容       |
| 数据难迁移或丢失   | 只有摘要、无法导出附件、无恢复路径           | 保留原件、明确导出与备份恢复要求，验收后才能宣称可靠     |
| 隐私范围扩大       | 默认全库送入 AI，公开页带出关联内容          | 先确定处理范围；公开与私密访问规则独立验收               |
| 文档负担反噬产品   | 每次小改动都重复维护大量文档                 | 文档按信息职责分开，关键变化才进入决策日志               |
| 首次好看但不常用   | 高层架构完整，日常入口不方便                 | 以真实捕获、找回、回顾场景验证；网页能否替代组件不可预设 |

## 7. 关键矛盾及待确认问题

这些问题不是要求重新讨论已明确的产品定位，而是决定第一版如何工作。建议仅需回复选项和必要补充；任何建议均不因未回复自动生效。

| 问题                    | 影响设计的矛盾                                                       | 可选决定                                                                                                                       | 当前建议及代价                                                                                         |
| ----------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Q1 入口与“持续提醒”     | 原始诉求是桌面小组件，后续核心是档案；首页常驻与主动通知不是同一体验 | A 首版手机／电脑网页显示当前关注，暂不主动通知；B 桌面可见的小组件是首版必要条件；C 首版还必须定时通知，可补充是否同时需要组件 | 暂建议 A 以减少入口开发范围；如果不在桌面可见就不会用，应选 B。不能替用户默认牺牲真实入口需求          |

| Q4 四种输入首版做到哪层 | 接收四类内容与全部 AI 理解是两种规模                                 | A 四类都可保存，优先语音转写，图片／链接深度解析后置；B 四类保存与 AI 理解都首版完成；C 首版先文字＋链接，语音／图片后续       | 建议 A，在覆盖输入需求和控制处理复杂度之间取舍。Q2 决定转写自动还是手动；四类原始内容仍须可保存和找回  |
| Q5 数据存放与 AI 范围   | 多端便利、个人隐私和自动关联可能互相牵制                             | A 接受云端同步，AI 首先只处理我明确选定的材料；B 接受云端及经授权的全库 AI 关联；C 优先本地保存，另行决定是否使用外部 AI       | 暂建议 A；须进一步确定哪些内容不得外发，再评估服务。尚不选择具体供应商，不把公开权限与 AI 权限混为一谈 |
| Q6 公开能力何时做       | 用户明确希望部分开放，但首版核心可先私人使用                         | A 首版私人使用，公开主页后置；B 首版就需要手动发布少量内容                                                                     | 建议 A；保留公开愿望及后续权限设计，不默认上线公开页面                                                 |

### 不必本轮逐项决定的细节

- 具体提醒时间和周期：Q1 确认需要通知后再决定；历史日／周／月／季度配置无效为默认授权。
- 灵感状态数量、标签规则、导航名称、搜索方式、记录模板：可在流程评审中简化决定。
- 附件大小、格式、性能阈值、离线行为和备份策略：根据真实样本及所选使用方式补入 PRD，不凭空填写承诺。
- 原始内容保留、导出、删除和恢复：在正式 PRD 中作为明确的待批准质量要求，不能因为它们合理就标成历史已确认。
- Codex 当前工程状态：需要其已有 PRD、Roadmap、开发报告或仓库核查结果才能判断。它不阻塞本轮需求分析，但影响后续交接和改造成本。

## 8. MVP 候选边界——供决策，不是冻结范围

本次建议优先验证“保存→找回→关注→回顾”的循环。其中“关注”是可选择的关联，不要求每条记录经过；“讨论”和“复盘”也不是所有记录的强制步骤。

| 候选能力                                    | 解决什么问题                 | 建议版本                     | 依赖决定                                    |
| ------------------------------------------- | ---------------------------- | ---------------------------- | ------------------------------------------- |
| 低摩擦保存四类原始输入                      | 用户主动提交的信息有可靠落点 | MVP 候选                     | Q4；存放方式依 Q5                           |
| 记录列表、编辑、基本搜索及原件访问          | 保存后能重新使用             | MVP 候选                     | 搜索首先覆盖哪些字段需在 PRD 确认           |
| 轻量灵感留存                                | 保留可能性，避免被迫执行     | MVP 候选                     | 不要求完整多阶段状态机                      |
| 当前重点、长期方向与可选下一步              | 记住当期正在做什么及原因     | MVP 候选                     | Q1、Q3                                      |
| 用户主动发起、基于选定材料的 AI 讨论        | 深入思考并找回已有观点       | MVP 候选                     | Q2、Q5；自动全库检索可后续                  |
| 可手动开始并保存的基础回顾                  | 连接积累与新的判断           | MVP 候选                     | 自动生成、周期通知不捆绑进入                |
| 语音转写                                    | 让语音能用于检索与讨论       | Q4=A 时优先                  | Q2 决定触发；失败仍保存原件                 |
| 原始内容／AI 结果区分、私密访问、导出与恢复 | 支撑长期信任和积累           | 建议作为首版质量底线，待批准 | Q5 及后续质量规格                           |

这不是建议同时开工的功能清单。确认六项决定后，需要再以真实使用场景压缩成可交付的一版；若小组件、全模态理解或公开页面必须前置，应相应延后其他能力，而不是累加。
