# Personal OS｜关键决策

> 用途：保存技术取舍的理由、状态和决策责任，防止建议被误当作产品批准。
> 状态：历史决定按现有证据补录；新产品方案等待用户确认。
> 更新：2026-11-06（Asia/Shanghai）。

## DEC-001｜Next.js、TypeScript 与 PostgreSQL 目标模型（补录）

- **背景**：用户优先考虑此技术栈，第一阶段需可运行响应式浏览器框架及数据设计。
- **可选方案**：Next.js 全栈基础；Vite SPA + 独立服务端；原生桌面优先。
- **最终方案**：当前采用 Next.js 16、React 19、TypeScript、Zod；Prisma 6.19.3 描述 PostgreSQL 目标模型；样式为原生 CSS 与 Lucide。
- **选择原因**：适合渐进接入服务端，类型与输入校验统一，当前界面规模无需额外样式依赖。
- **放弃其他方案的原因**：拆分后端增加首阶段维护面；原生桌面超出明确范围。前轮开场曾提 Tailwind，实际未采用，按代码事实记录。
- **潜在风险**：框架升级兼容性；当前聚合页面组件后续可能需要拆分；Prisma 原生引擎受网络约束。
- **决策人及状态**：Codex 提出并已在工程采用；用户指定技术偏好，不等于审核所有实现细节；数据库上线待验证。

## DEC-002｜第一阶段使用本地状态与版本化 JSON（补录）

- **背景**：空仓库需先提供能操作的产品框架，用户未要求首阶段完整后端/部署。
- **可选方案**：localStorage；IndexedDB；直接接入认证与 PostgreSQL。
- **最终方案**：浏览器 localStorage，v1 Zod 结构、导入覆盖确认、完整 JSON 导出。
- **选择原因**：启动无外部凭据，能验证记录、检索、确认、灵感与复盘基本流程。
- **放弃其他方案的原因**：IndexedDB 并非当前演示的必要前提；完整后端引入认证、数据库和对象存储，扩大首阶段工作量。
- **潜在风险**：容量、清除浏览器数据、多标签并发、无加密和账户隔离；此方案不是长期真实敏感数据存储承诺。
- **决策人及状态**：Codex 已实施的阶段性选择；长期存储和下一轮优先级待用户使用需求确认（Q-07）。

## DEC-003｜原文、AI 结果和目标提案分离（补录）

- **背景**：用户明确要求 AI 不覆盖原文、不未经确认修改目标。
- **可选方案**：直接改写对象；独立结果与待确认提案。
- **最终方案**：本地 record.ai 与 raw 分开；演示提案单独存储、校验 pending 和明确确认；Prisma 目标模型分离 ProcessingResult 与 GoalProposal。
- **选择原因**：保持原始经历和用户决策权，后续可加入来源与版本审计。
- **放弃其他方案的原因**：直接覆盖违背明确产品原则。
- **潜在风险**：当前无真实 AI/后端权限；本地 confirmed 布尔值不是安全授权机制；数据库事务和版本冲突仍未实现。
- **决策人及状态**：用户规定原则，Codex 实施第一阶段结构；结构/本地确认已测试，真实 AI 权限待实现。

## DEC-004｜文档迁移为六模块、单一正文

- **背景**：已有五份扁平文档，本轮要求完整文档体系且不重复创建。
- **可选方案**：原路径与新路径双份正文；直接删除旧路径；迁移正文并留指引。
- **最终方案**：迁移已有正文到对应模块，旧路径仅保留短指引；docs/README 作为导航。
- **选择原因**：复用已有材料，已有聊天/README 链接仍能找到文档，只维护一份事实。
- **放弃其他方案的原因**：双份容易失步；直接删路径破坏已有引用。
- **潜在风险**：引用路径需要核对；旧文件只应更新指向，不能重新积累独立正文。
- **决策人及状态**：Codex 根据本轮明确文档授权执行；文件迁移已完成，校验结果见核查报告。

## DEC-005｜下一轮优先修正关注与方向关系（提案）

- **可选方案**：先做关注闭环；先做记录意图；先接真实数据库/账户。

- **选择原因**：直接回应核心产品定位，降低后续数据和 AI 设计建立在含混概念上的风险。
- **暂缓其他方案的原因**：意图也重要但不解决当前首页关系差距；服务端是否更紧迫取决于跨设备需要，尚无用户反馈。
- **潜在风险**：对象拆分和历史迁移可能扩大范围；需先确认关联数量、关注顺序和结束机制；若跨设备更急则重新排序。

## DEC-006｜模型校验与数据库就绪分开报告（补录及持续规则）

- **背景**：前轮 Prisma 原生引擎校验和下载遇到 403，第一阶段不依赖数据库运行。
- **可选方案**：申请必要网络配置后执行原生命令；使用官方 WASM 做离线模型校验；关闭校验以下载（不可接受）。
- **最终方案**：正常工作流用锁定版本的 Prisma 官方库 getDMMF 校验；明确迁移/读写未执行。需要原生引擎时再走受支持的网络配置流程。
- **选择原因**：在不放弃完整性校验的前提下完成当前模型验证。
- **放弃其他方案的原因**：本轮无需数据库，不扩大网络设置范围；关闭 TLS/校验和违背完整性要求。
- **潜在风险**：WASM 不能证明真实 PostgreSQL 权限、约束执行和事务行为。
- **决策人及状态**：Codex 已采用；本轮 13 模型校验通过；原生引擎下载未重试，历史 403 不当作当前重新测得的事实。

后续决策沿用以上八项字段。重大范围未获用户确认时，“最终方案”必须保留待确认状态。

## DEC-007｜Supabase 云端与会话权限方案（T01 提案）

- **背景**：R0.1 D13 已确认云同步，D14 首版私人；PRD F07/A10 包括原图与搜索的未授权访问拒绝。
- **可选方案**：Next.js+Supabase 全套；Next.js+独立 PostgreSQL/S3/Auth；完全自托管。
- **最终方案**：待确认。推荐 Supabase PostgreSQL/Storage/Auth 与现有 Next.js；Vercel 可选。用户 JWT/RLS 和受控事务支撑 CRUD；原图由会话鉴权入口读取。
- **选择原因**：复用界面、减少单人项目运维，数据及对象权限保持清楚。
- **暂缓其他方案的原因**：自建基础设施维护更多；普通 Prisma 高权限连接不会自动获得 Supabase JWT/RLS 保护；签名读 URL 可转发，不单独作为 A10 防线。
- **潜在风险**：供应商锁定、区域可达性、费用与条款未核实、策略配置错误、DB/对象非原子一致性。
- **决策人及状态**：Codex 技术建议，Owner 审核 D16/O04；未创建资源、未实施、未批准付费。

## DEC-013｜批准私有数据基础与显式权限收紧

- 背景：2026-11-07 Owner 明确批准按方案建立数据库与私有权限基础；新环境域名已生效。实际仅有客户端密钥，不能执行 DDL。
- 可选方案：请求管理凭据、使用已有管理工具、准备 SQL Editor 一次性脚本；依赖默认 grant 或显式收紧新对象授权。
- 最终方案：复用已批准契约，生成含本人邮箱匹配的私有安装文件交由 SQL Editor 执行；显式 revoke 后最小 grant，事务绑定已验证用户，遇旧对象/策略即停止。
- 原因：不要求增加管理密钥，避免人工复制 UID 错误；Supabase 默认 grant 可能包含 DELETE/TRUNCATE，RLS 本身不限制 TRUNCATE，故必须显式撤权以落实批准的原件保留边界。
- 放弃其他方案原因：当前无管理工具或连接；让公开客户端密钥执行 SQL 不可行；盲目重复建表或覆盖旧策略违背保留原则。
- 潜在风险：真实 Supabase 的默认角色、既有策略、账号验证仍需现场核查；脚本通过内存测试不能替代 A10，安装成功也不能替代用户验收。
- 决策人及状态：Owner 批准产品范围与基础数据库操作；Codex 修正权限实现并准备执行交接；实际云端执行待完成，不重复征求已批准范围。

## DEC-016｜可恢复回收站与数据库保护

- 背景：Owner 发现过去/未来/复盘没有删除入口，明确批准移入/查看/恢复方案及数据库调整。
- 选项：物理删除、独立墓碑表、现有表增加可空 deleted_at。
- 最终方案：原记录/entry 增加 deleted_at，独立 RPC 以版本和幂等 key 移入/恢复；原文/附件不变，普通列表隐藏，设置统一回收站；方向关联由 DB 触发器保护。
- 原因：增量小、无数据搬移，现有原件保护兼容；保留来源 ID 和灵感标记，恢复无需复制内容。
- 未选原因：物理删除违背保留原则；墓碑表增加关联/并发同步复杂度，本轮无必要。
- 风险：需要一次远端增量安装；平台无管理连接，需 Owner SQL Editor 执行；真实并发压力和用户云端复验待完成。底层本人存储访问保持原权限，回收站不等于不可恢复销毁。
- 决策人/状态：Owner 批准产品范围；Codex 实现技术方案和隔离验证，远端执行未确认；不扩大到永久删除/自动清理/改目标。

## DEC-017｜云端完整导出与保守补入恢复（默认规则已确认）

- 日期：2026-11-08（Asia/Shanghai）。决策人及状态：Codex 提出技术建议；Owner 已确认完整范围、手动未加密 ZIP、不覆盖恢复合同，批准先推进 BKP-01～03；恢复写入后续实施。
- 背景：设置仅有旧版 localStorage JSON 导出；正常云端列表排除回收站，附件在回收站详情入口不可读。云同步与回收站均不能代替独立备份。
- 可选方案：仅元数据 JSON；JSON＋原始附件 ZIP；只依赖 Supabase 平台备份；另有加密包或自动云盘备份可选。恢复可选择覆盖、复制重映射，或相同跳过/冲突停止/补入缺失。
- 最终方案：Owner 已确认手动全量未加密 ZIP（明确隐私提示），包含回收站及所有绑定原件；先导出与本地校验，再预检、确认补入和隔离演练。相同完整内容跳过，同 ID 有差异整批停止；不覆盖或清空已有档案。
- 选择原因：可离线阅读、可迁移且能校验原件；保护当前数据与目标；分阶段获得真实资源和恢复证据后再上线写入。
- 放弃其他方案的原因：仅 JSON 不能完整保全原件；平台备份能力/套餐尚未核验，也不能直接替代用户可读档案。覆盖及自动复制扩大数据变更范围；自动云盘/加密增加交付范围，未加密首版仍须 Owner 明确同意，可在实现前改为成熟认证加密方案。
- 潜在风险：ZIP 隐私与手机资源限制、快照和 Storage 一致性、回收站来源触发器、旧版本格式兼容；Storage 与 DB 不能一起回滚，失败上传可能留下私有暂存，不能承诺零残留或擅自清理。
- 实施前置：Owner 已确认[具体方案](../02-engineering/cloud-backup-restore-v0.1.md)；BKP-01 验证容量/下载；只读 RPC 和恢复批次/权限分别评审。BKP-02 已另附并隔离验证只读增量；不更改原件保护或使用常规 service-role 绕过。

## DEC-018｜STORE ZIP、受限 Blob 与本地 Worker 校验

- 日期：2026-11-08。决策人/状态：Codex 工程实现，基于已批准 BKP-01～03；开发环境验证，未部署。默认产品规则见 DEC-017。
- 背景：原图不应重编码；Render 内存与手机文件 API 不能假定无限；要在所有原件验证后才允许下载成功。
- 可选方案：整包 base64 JSON；服务端流式 ZIP＋浏览器原生直接落盘；服务端流式 ZIP＋有限 Blob＋Worker；持久后台导出任务；加密包。
- 最终方案：锁定 fflate 0.8.3（发布核查由 0.8.2 升补丁，修复 GHSA-px8p-9vwx-vf98）以 STORE 逐文件生成，终末清单/目录只在完整原件校验后发出；浏览器使用限定容量 Blob，Worker 校验，再由用户显式点击保存。只读 SQL 语句快照、身份 RLS 及既有私有存储，不新增存储服务或持久导出任务。
- 选择原因：JSON＋原件可离线阅读，原件不重压；Web Worker 避免校验阻塞 UI；普通下载链接兼容范围较广。限制 STORE 子集且不解压能拒绝压缩炸弹，独立校验 CRC/SHA/目录/引用，不执行包内容。
- 放弃原因：base64 增加体积；浏览器直接流式落盘 API 兼容性不足且难在失败时撤回残包；后台任务扩大范围；加密不在已确认首版内。
- 风险：Blob/Worker 仍占内存，严格 ZIP 子集不支持重打包文件；容量/120 秒/单进程并发防护是当前工程边界，不是生产性能承诺；多实例限流、断点续传、iOS 实际体验未验证。SQL/数据与 Storage 跨系统一致性依赖原件不可覆盖及逐件哈希；只读增量未远端执行。
- 证据与后续：[实施交接](../02-engineering/cloud-backup-export-implementation.md)列出 50 MB 原件、1,000 附件、5,000 条记录实测；上线先做真实下载与原件哈希核验，再推进恢复预检。

## DEC-019｜复用快照的只读预检，不创建恢复批次

- 背景：BKP-04 获 Owner 明确批准；现有格式可本地校验，快照不含未绑定附件。
- 可选方案：上传完整 ZIP；只发摘要哈希；显式同意后发送文字与结构化元数据。
- 最终方案：经同意发送结构化 snapshot，服务端独立校验后与本人快照比较，再查候选附件是否已有未绑定占用；全部只读，无 schema/权限变更。
- 原因：原件无需上传，保留字段/引用以独立验证内容结构与差异；可复用已安装 RLS。
- 放弃其他方案原因：ZIP 上传增加原件传输与临时存储范围；仅摘要无法独立验证候选结构/当前约束，需额外协议和可信边界设计。
- 风险：元数据含原文，必须明确告知且不自动发送；两次读取不是持续锁定，未重新下载云端原件验证；预检不是恢复授权或可恢复证明，后续写入须重校验。
- 决策人/状态：Owner 批准只读范围，Codex 提出并实现技术方案；测试与真实联验分别记录。
